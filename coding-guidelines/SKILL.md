# 编码准则

按任务类型应用相关规则，审查、诊断和方案评估以分析与建议为交付；代码修改依据用户请求执行。

用户的要求、仓库中的明确指令和项目约定的优先级高于本准则。

## 编码前先思考

先阅读相关代码并定位问题或理解需求，解决可能的歧义，分析需要改动的范围，再开始修改。

- 先通过代码、文档和相关验证澄清关键不确定性，已有明确授权的事项按授权执行。
- 若仍需用户决定任务范围、用户可见行为或契约取舍时，说明具体影响并询问。
- 对于低风险细节，采用合理假设并继续，仅在假设影响结果理解时说明。
- 谨慎参考仓库已有代码模式，它们未必是正确的范式。

## 控制改动范围

在理解目标和验收标准的基础上，以最小的完整改动完成目标。

- 改动应该聚焦于任务涉及的代码或文档。
- 实现当前需求所必需的功能，抽象与配置应有足够理由支撑。
- 语义和职责相同的功能优先复用已有代码，使用简单的实现方式。
- 保留无关的本地修改、未跟踪文件和用户创建的产物。
- 完成改动后，执行与改动直接相关且有价值的验证，不要机械运行无关检查。
- 验证结论以实际执行结果为依据，明确区分通过、失败、未执行和受阻。

每一处改动都应能追溯到所请求的行为，或是维持改动正确性所必需的内容。

## 维护单一信息源

相同业务规则、约束或知识应尽量只有一个权威实现或来源。

- 语义和职责相同的功能应尽量只有一个实现，并由其它位置复用。
- 相同事实或规则应有一个明确的权威来源，其它位置优先引用而非复制。
- 对于关键的约束和规则边界，允许在文档中少量重复。

单一信息源的价值在于明确的信息组织，并防止开发过程中可能的漂移。

## 保证测试质量

测试应保护可观察行为、明确契约或有实际价值的边界条件。

- 对行为变更、bug 修复、业务规则和有实际意义的错误路径，优先编写回归测试。
- 除非相关内容属于契约，否则避免测试文档或 UI 的精确措辞、私有实现细节、mock 调用顺序，以及文件、日志或缓存等副产物。
- 不要为了满足 TDD、提高覆盖率或证明代码已编写而添加不必要的测试。

测试代码也需要维护，编写测试应出于实际需要而不是形式正确。

## 保持简要输出

用户的注意力和时间相较于 Token 是稀缺资源，回复用户的内容应保持简洁明确。

- 汇报完成结果、重要决定、相关验证状态，以及影响用户判断的限制或阻塞项。
- 使用准确的技术术语，并保持需要的代码块和关键报错信息不变。

默认给出足以支持用户下一步判断的最短回复，用户要求解释时再展开。
